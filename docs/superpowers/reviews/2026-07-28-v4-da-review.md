---

The approach choice (ICS aggregation over OAuth / publish-outward) is right and I'm
not challenging it. Every finding below is inside Approach 1's execution.

## CRITICAL

### 1. `WKST` alone will send most Google recurring events to `skipped`

**Mechanism.** Plan Task 4: supported set is `FREQ|INTERVAL|BYDAY|UNTIL|COUNT`;
"**Anything else in the rule** … → the whole event goes to `skipped`". Google
Calendar routinely emits `WKST` on weekly rules. A real Google class-schedule rule
looks like:

```
RRULE:FREQ=WEEKLY;WKST=SU;UNTIL=20261218T045959Z;BYDAY=MO,WE,FR
```

Under the plan's stated policy, `WKST` is "anything else" → the entire semester of
Statics lectures lands in `skipped`, and the settings row reads "1 event skipped."
This is the exact "skip policy guts the feature" failure the design was supposed to
avoid.

**Change.** Split the RRULE parts into three explicit lists in the spec: *supported*,
*ignorable-when-harmless* (`WKST` — only affects `WEEKLY` with `INTERVAL>1`; `X-*`),
and *skip-triggering*. Add a test: the rule above expands correctly, and
`FREQ=WEEKLY;INTERVAL=2;WKST=MO` either handles WKST or skips with reason
`unsupported_wkst`. Do not use a permissive "ignore unknown parts" catch-all — that
is the fallback the constraints forbid.

### 2. Ordinal `BYDAY` (`BYDAY=2TU`, `BYDAY=-1FR`) is unsupported and it is common

**Mechanism.** Plan Task 4: "`BYDAY` (weekly only). MONTHLY follows DTSTART's
month-day." Google Calendar's repeat UI offers "Monthly on the second Tuesday" as a
first-class option and emits `RRULE:FREQ=MONTHLY;BYDAY=2TU`. Apple Calendar offers
"last Friday of the month" → `BYDAY=-1FR` (often with `BYSETPOS=-1`). Club meetings,
lab sections, office hours, and recurring advisor meetings are overwhelmingly this
shape. All of them go to `skipped`.

Secondary consequence: VTIMEZONE DST rules are `FREQ=YEARLY;BYMONTH=3;BYDAY=2SU`.
Without ordinal BYDAY you cannot evaluate a feed's own VTIMEZONE even if you decide
to (see Major 9).

**Change.** Move ordinal `BYDAY` for `MONTHLY`/`YEARLY` into the supported subset in
the spec and into Task 4's test matrix (`2TU`, `-1FR`, and the "5th Monday doesn't
exist this month" case). Also promote single-value `BYMONTHDAY=15` and `BYMONTH` —
both are cheap and both appear in ordinary calendars.

### 3. `Intl.DateTimeFormat` cannot perform the conversion Task 3 specifies — it runs the wrong direction

**Mechanism.** `Intl.DateTimeFormat` maps an *absolute instant* → wall clock in a
zone. `icsDateToLocal` needs the inverse: a *wall clock in the feed's TZID* →
absolute instant → wall clock on the device. Nothing in the design or plan
acknowledges the inversion. I ran it:

```
naive format of UTC 09:00 into NY => 09/01/2026, 05:00
```

Feeding `DTSTART;TZID=America/New_York:20260901T090000` through the obvious reading
of the plan gives 05:00, not the correct 13:00 UTC — off by 2× the offset. An
implementer following the plan literally writes this bug.

The correct approach is offset inversion (probe an instant, format into TZID, measure
the residual, re-probe, verify), and it has two documented failure states the plan
never mentions. Both confirmed:

```
two distinct instants, same NY wall clock: 11/01/2026, 01:30 | 11/01/2026, 01:30   ← ambiguous (fall-back)
gap: no instant formats to 03/08 02:30 -> 03/08/2026, 03:30                        ← nonexistent (spring-forward)
```

**Change.** Specify `zonedWallClockToInstant(parts, tzid)` as its own exported,
separately tested function with an explicit written policy for the ambiguous hour
(RFC 5545 convention: take the *first*/DST offset) and the gap (shift forward by the
gap width, or skip with reason `nonexistent_local_time` — pick one and write it
down). Test matrix must include: fall-back ambiguous hour, spring-forward gap, and a
southern-hemisphere zone (`Australia/Sydney`) where the DST sign inverts. This is the
highest-risk algorithm in V4 and the plan currently gives it one parenthetical.

### 4. `EventInstance`'s shape violates contracts the existing code already imposes

The design defines `EventInstance: { uid, title, date, time, endTime, feedId }`.
Three existing call sites break:

**(a) `sortItemsByDate` becomes a non-antisymmetric comparator.** `js/items.js:40`
compares `a.createdAt < b.createdAt`. With `createdAt` present on own items and
absent on external ones, both `cmp(own,ext)` and `cmp(ext,own)` return `1`.
Confirmed:

```
order A: [ 'Bbb own', 'Aaa ext', 'Ccc ext' ]
order B: [ 'Aaa ext', 'Bbb own', 'Ccc ext' ]
order C: [ 'Aaa ext', 'Ccc ext', 'Bbb own' ]
stable across input orders? false
cmp(own,ext)= 1   cmp(ext,own)= 1
```

Failure scenario: a background sync completes, `instancesForRange` returns instances
in a different array position, and the List view reorders items *that did not
change*. Same date, same time, different order. This will read as a rendering bug and
be very hard to trace.

**(b) `it.type` is absent** → `js/app.js:166`, `js/app.js:212`, `js/weekview.js:26`,
`js/dayview.js:34,65` all do `'type-' + (it.type || 'general')`. Every external item
silently becomes `type-general` warm-gray, not the feed color. The plan's File
Structure table lists `dayview/weekview/calendar` as "modify" but omits that two of
the five class-name sites live inline in `app.js`'s `renderList`/`renderCalendar`.

**(c) `it.id` is absent** → `js/dayview.js:47` unconditionally builds a × and calls
`onDelete(row.item.id)`; `deleteItem` filters `items` by that id and silently matches
nothing. The user taps ×, nothing happens, no message.

**Change.** Fix the contract in the spec, not in the views: `EventInstance` gains
`id` (`${feedId}:${uid}:${date}:${time}`), `createdAt` (use the instance's own
`date+time` so the comparator stays total), and `external: true` consulted at every
class-name site. Add a Task 7 test asserting `sortItemsByDate` over a mixed array is
order-independent — that test is the one that would have caught this.

### 5. `DURATION` and absent `DTEND` are not handled anywhere

Neither document mentions `DURATION`. `ParsedEvent` carries `dtstart, dtend` and
nothing else. RFC 5545 permits `DTSTART` + `DURATION` in place of `DTEND`, and
permits neither (DATE → one day; DATE-TIME → zero duration).

Failure scenario: a VEVENT with `DTSTART;TZID=…:20260901T090000` + `DURATION:PT1H`
has no `dtend`. Under "zero fallback" it either goes to `skipped` (silent feature
loss on whatever fraction of a feed uses DURATION) or renders with `endTime: null` (a
silent wrong duration — precisely the degradation the Global Constraints forbid). The
plan forces the implementer to invent this rule mid-task.

**Change.** Add `DURATION` (at least `P#DT#H#M`, `PT#H`, `P#D`) to Task 4's interface
and tests, and write the no-DTEND rule explicitly: `VALUE=DATE` → one day;
`DATE-TIME` → `endTime: null`, which maps cleanly onto V3's existing "timed item
without endTime → pinned chip" (`js/timegrid.js:44`).

### 6. List view has no range to give `instancesForRange(feeds, cache, start, end)`

**Mechanism.** Task 7: "`app.js` builds `visibleItems(range)` … all four views
consume the merged array." Month, Week, and Day all have natural ranges. **List does
not** — `renderList` (`js/app.js:155`) renders every item that exists, unbounded.
Lazy-per-range expansion has no bound to hand it, and an unbounded `FREQ=WEEKLY`
RRULE has no terminating expansion.

There are only three outcomes and the design picks none: List shows no external
events (feature hole), List expands everything (non-terminating on unbounded rules),
or List gets an invented horizon (undocumented, and own items will still extend past
it — so the list ends with own-items-only, which looks broken).

**Change.** The spec must state List view's external horizon explicitly (e.g. `today`
→ `today + 365d`), state that own items beyond it still render, and decide whether to
show an end-of-external marker. This blocks Task 7 and cannot be resolved by the
implementer without a product decision.

### 7. `/feed` is an open proxy; the design's "Not an open proxy" claim is false

**Mechanism.** The three stated mitigations are `https:`-only, `BEGIN:VCALENDAR`
prefix check, and a 1 MB cap. The prefix and size checks happen **after** the
upstream fetch completes — the victim origin receives every request regardless. There
is no authentication, no rate limit, and no origin check. `WORKER_URL` is a public
`workers.dev` hostname in `js/config.js`, committed to a public repo.

Failure scenario: someone enumerates `workers.dev` subdomains, finds
`…/feed?url=https://victim.example/anything`, and gets a free, unauthenticated,
IP-anonymized request relay backed by Cloudflare's network. Consequences land on
Alex: the Worker's free-tier request budget is shared with smart-add, so exhausting
it takes `POST /` down too, and abuse reports attach to his account. The existing
endpoint's stated ceiling ("monthly spend cap in the Anthropic Console",
`worker/src/index.js:43`) does not apply — `/feed` burns Worker requests, not tokens.

Additionally, the `https:`-only check is defeated by redirects (see Major 11).

**Change.** Three cheap fixes, all in Task 5:
- Enforce `request.headers.get('Origin') === ALLOWED_ORIGIN` server-side and 403
  otherwise. Browsers cannot forge `Origin`; this stops all automated/casual abuse
  for ~3 lines. (Note: `worker/src/index.js:2` claims `env.APP_PASSPHRASE` is a set
  secret while line 43 says it is unused — if it exists, requiring it on `/feed` is
  even stronger.)
- Reject private/loopback/link-local hosts and non-standard ports before fetching.
- Add a Cloudflare Rate Limiting rule on the `/feed` path, or a bounded per-IP
  counter.
- Change the spec's wording; "Not an open proxy" as currently justified is not
  defensible.

## MAJOR

I found nine Majors, which is more than the design should be carrying. That count
concentrates in one section — **"Client: `js/ics.js`" in the spec needs rework, not
patching** — and that is reflected in the verdict.

### 8. No real feed data enters the project until Task 9, the last task

The spec says fixtures will be "**modeled on** real Google / iCloud / Outlook /
Canvas output shapes" — meaning invented from the implementing agent's memory.
Criticals 1, 2, 5 and Major 9 are all *exactly* the class of error that invented
fixtures reproduce faithfully, because the same memory writes the fixture and the
parser. Live verification is deferred to Task 9 "with Alex," after all nine tasks are
built on the unverified subset.

**Change.** Insert a Task 0: capture 3–4 **real, non-secret** feeds as byte-exact
fixtures before Task 2 — Google's public holiday ICS is genuine Google output, and
public iCloud/Canvas demo calendars exist. This costs one task and converts "modeled
on" into "captured from," falsifying the RRULE/TZID subset on day one instead of day
nine. This is the single most leveraged change in the review.

### 9. The Outlook Windows-TZID bet is unverified, its failure mode is total, and the design throws away the data that would fix it

Task 3 specifies: non-IANA TZID (e.g. `W. Europe Standard Time`) → throw
`UnsupportedTz` → skip the event. Exchange/Office 365-lineage published calendars
commonly emit Windows zone IDs (my confidence on the exact consumer-`outlook.live.com`
split is **moderate**, not high — which is itself the problem). If they do, the
outcome is not degraded: **every Outlook event is skipped and the feed renders
empty**, with a settings row reading "412 events skipped."

The design compounds this by stating VTIMEZONE is ignored — but VTIMEZONE is inside
the feed and contains `TZOFFSETTO` for STANDARD and DAYLIGHT plus the switch RRULEs.
No timezone database is needed; the answer ships with the payload.

**Change.** Two options, pick one in the spec: (a) parse VTIMEZONE `TZOFFSETTO` and
select STANDARD/DAYLIGHT via the block's own RRULEs — this requires ordinal `BYDAY`
(Critical 2), so the two fixes compose; or (b) ship a small static Windows→IANA map
(~130 entries, the CLDR `windowsZones` list, public domain). Either is bounded work.
Whichever you choose, Task 0 (Major 8) must confirm what Alex's actual Outlook feed
emits *before* Task 3 is written.

### 10. `INTERVAL` phase relative to DTSTART is missing from the plan and its tests

**Mechanism.** Task 4: "UNTIL/unbounded rules iterate only within the requested
range." For `INTERVAL=1` that is fine. For `FREQ=WEEKLY;INTERVAL=3` you must compute
the cycle phase from DTSTART — `floor((rangeStart − dtstart)/period)` — before
iterating, or instances land on the wrong weeks. This fails **silently**: correct
count, plausible-looking dates, no `skipped` entry, no signal.

Failure scenario: a biweekly lab section with `DTSTART:20260901`, viewed in November.
Iterating from range start puts the labs on the alternate weeks — every one wrong,
and nothing in the app says so.

**Change.** Name phase computation in Task 4's interface. Add the test the current
matrix lacks: `INTERVAL=3` weekly, range starting 10 weeks after DTSTART, assert
instances land on weeks 12 and 15 — not 10 and 13. The existing "`INTERVAL=2`
weekly" test will pass with the broken implementation if the range starts at DTSTART.

### 11. Redirects break iCloud and void the https-only guarantee

Workers' `fetch` follows redirects by default and does not re-run your validation on
each hop. So `https://attacker/` → `302 http://internal` defeats the scheme check
entirely (compounding Critical 7). Disabling redirects is not an option either:
iCloud published calendars are served from sharded `p##-…icloud.com` hosts and
genuinely redirect — one of the four named providers.

**Change.** Task 5 uses `redirect: 'manual'` with a bounded follow loop (max 3 hops)
that re-runs the full URL validation on every hop. Test both directions: an
iCloud-style 302 to another https host succeeds; a 302 to `http://` or a private
host 400s.

### 12. Task 5's test approach has no precedent in this repo and the File Structure table is missing a file

`worker/tests/` contains only `normalize.test.js` and `prompt.test.js` — both test
*pure helper modules*. **`worker/src/index.js` has zero tests today.** Task 5's
instruction "extract route-handling into testable functions **as the existing worker
tests do**" describes a precedent that does not exist. Under `node --test` with zero
deps, `caches.default` and Workers' `fetch` are absent globals; "mock fetch/caches"
is stated with no mechanism.

Separately, the route split is a rewrite of the entry point, not an addition:
`worker/src/index.js:34` returns 405 for any non-POST *before* any routing, and
`cors()` (line 9) hardcodes `content-type: application/json` and `Allow-Methods:
POST, OPTIONS`.

**Change.** Add `worker/src/feed.js` to the File Structure table, exporting
`handleFeed(request, { fetchImpl, cache })` with both effects injected — mirroring
exactly how `prompt.js`/`normalize.js` are already split out of `index.js`.
`index.js` stays a thin, untested wiring layer. Add a regression test that `POST /`
and `OPTIONS` behave unchanged.

### 13. The 15-minute edge cache makes "Sync now" a lie

The design gives every feed a manual **Sync now** button and simultaneously caches
`/feed` at the edge for ~15 minutes keyed on the target URL. Failure scenario, and it
is the *first* thing Alex will do on day one: add an event in Google Calendar, open
plaenicke, tap Sync now, see nothing, tap again, still nothing, conclude V4 is
broken. The status line will cheerfully read "synced 3s ago."

**Change.** Manual sync must bypass the edge cache (cache-busting param, or a
`Cache-Control: no-cache` request header the Worker honors); only background
`syncStale` uses it. Also: Google's own iCal export lags its UI by a meaningful
margin, so the status line should say what it means — "fetched 3s ago," not
"synced" — or the same complaint arrives via a different route.

### 14. V3's view caps were tuned for own-items density; four feeds invalidate that, and the show/hide YAGNI call is wrong

Month cells show 2 chips (`js/calendar.js:29`), week columns cap at 8 blocks
(`js/weekview.js:25`), both ordered by `chronoFirst` — timed first. Add a Google
calendar with 6 timed events on a Tuesday and Alex's untimed "essay due" is never a
chip; it lives permanently behind "+4 more". The design asserts these "just work."
Mechanically yes; semantically the external feed evicts the user's own planner from
his own planner.

Two aggravating factors the design doesn't cover:
- **Multi-day *timed* events are unhandled.** The spec covers "overnight" and
  "multi-day *all-day*", but not a 3-day timed event (DTSTART Fri 09:00, DTEND Sun
  17:00 — people create these). Generalizing the overnight split gives a 00:00–23:59
  block on the middle day, which under `layoutDayBlocks` (`js/timegrid.js:41`)
  overlaps everything and squeezes every other item that day to 1/n width. A
  week-long timed event makes seven days of Day view unusable.
- The **show/hide toggle** is deferred as YAGNI with "remove/re-add is the
  workaround." That reasoning is wrong: removing a feed deletes its cache, and
  re-adding requires re-pasting a secret capability URL — for Google that means going
  back into Calendar settings, in practice on a desktop. The workaround costs minutes
  and a second device; the feature is a boolean on the feed record plus a filter in
  `instancesForRange`. YAGNI needs *both* speculative demand and a cheap workaround;
  neither holds.

**Change.** Cap the overnight split at 2 days and render longer timed spans as
untimed "Other tasks" entries per covered day (decide it in the spec, test it in Task
4). Reserve at least one month-chip slot for own items, or raise the caps. Move the
per-feed toggle into V4.

### 15. localStorage budget is asserted without a number, and there is no quota-failure path

The spec claims parsed records "keep the cache far under localStorage limits" with no
estimate. Order of magnitude: a Canvas ParsedEvent (long `…@instructure.com` uid,
title, two dates) is roughly 200 bytes of JSON; a Canvas feed spans every enrolled
course including past terms. Four feeds plausibly land at 0.2–2 MB against iOS
Safari's ~5 MB per-origin ceiling — shared with `plaenicke.items`.

More concretely: `js/storage.js:30` is a bare `localStorage.setItem` with no
try/catch, while `js/settings.js:63` already wraps writes ("private mode") — the
codebase knows this throws. Task 1 does not mention quota at all. A
`QuotaExceededError` from a feed-cache write is an uncaught exception in the sync
path.

**Change.** Task 1 wraps cache writes; define the over-quota policy explicitly (drop
the largest/oldest feed cache entry, prune events outside a window) and **surface it
in the feed's status row** rather than degrading silently. Put a size estimate in the
spec so the claim is checkable.

### 16. `UNTIL` comparison semantics are undefined and off-by-one at the boundary

`UNTIL` has three real forms: UTC (`20261218T045959Z` — required for DATE-TIME
DTSTART, what Google emits), DATE (`20261218` — for all-day rules), and naive local
(technically invalid, common in the wild). The plan lists `UNTIL` as supported with
one test and never says whether the comparison happens on absolute instants or on
converted local dates.

Failure scenario: `UNTIL=20261218T045959Z` is Dec 17 23:59 EST. Compare against
locally-converted instance *dates* and you wrongly include a Dec 18 instance — one
extra lecture at the end of every semester course.

**Change.** State in the spec that `UNTIL` is compared on absolute instants; handle
the DATE form separately; decide whether naive-local `UNTIL` is accepted or skipped.
Add the boundary test explicitly.

## MINOR

17. **`skipped` accounting undersells the loss.** One skipped uid can be an entire
    semester of instances. "2 events skipped" is technically true and practically
    misleading — it violates the spirit of zero-fallback while satisfying its letter.
    Include `summary` in the skipped record and surface it: *"2 skipped: 'Statics
    Lecture' — unsupported recurrence."* Roughly free.

18. **`render()` renders all four views on every call** (`js/app.js:257`), so one
    re-render triggers four `instancesForRange` expansions over four ranges — on
    every prev/next arrow tap, on a phone, over a Canvas feed with unbounded rules.
    Memoize expansion per `(feedId, rangeStart, rangeEnd)`, invalidate on sync.

19. **Multi-feed sync should debounce to one re-render.** Task 7 says "one re-render
    when any feed updates" — ambiguous between per-feed and settled. Four feeds →
    four full four-view rebuilds. Specify: debounce until all in-flight syncs settle.

20. **"No fixed horizon" is a claim about expansion, not data.** Navigate to a month
    two years out and external events are absent because the *provider's* feed
    doesn't contain them — indistinguishable from "no events." Scope the claim in the
    spec.

21. **"Background sync" is misleading on iOS.** It is an async fetch on app load, not
    the Background Sync API; a home-screen PWA is killed aggressively and there is no
    periodic wakeup. The 30-minute staleness policy implies otherwise. One clarifying
    sentence.

22. **Orphan-cache pruning has two owners.** Task 1 says "pruning is feeds.js's job";
    Task 6's interface list has no prune function; Task 8 puts deletion in
    `settings.js`. Pick one, give it a test.

23. **Cache key vs. the privacy claim.** The spec says the Worker must never log feed
    URLs, then keys `caches.default` on the target URL — the capability token becomes
    the cache key. Acceptable for a personal zone; worth one honest sentence rather
    than an unqualified privacy claim.

24. **`\N` (capital) is also a newline** per RFC 5545 and appears in
    Microsoft-generated output. Task 2's `unescapeText` lists only `\n`. One-line
    fix, one-line test.

25. **`process.env.TZ` at runtime does work** — verified on Node v22.18.0 that
    mutation takes effect for both `Date` and `Intl`. So the plan's approach is not
    broken here. It is still the wrong design: it makes the pure module read an
    implicit ambient zone, and `node --test` may run files concurrently. **Change:**
    pass the target zone explicitly — `icsDateToLocal(value, params, targetTz)`, with
    `app.js` supplying `Intl.DateTimeFormat().resolvedOptions().timeZone`. Fully
    deterministic tests, zero env manipulation, and it makes the Critical-3 test
    matrix trivial to write.

## On the brief's assumptions A1–A5

A1–A4 are sound and I have no concrete reason to challenge the rejections of
Approach 2 or 3 — the cost accounting is honest and the backlog placement is right.

**A5 ("iPhone-first") is load-bearing in an unexamined way.** It is treated as a
UI-layout assumption, but it silently determines three technical constraints that
shape V4: the ~5 MB Safari localStorage ceiling (Major 15), the absence of any real
background execution (Minor 21), and Safari as the sole `Intl` implementation the
timezone code must satisfy (Critical 3). None of those are traced back to A5
anywhere. Recommend restating A5 as a technical constraint with those three
consequences named, so they get designed for rather than discovered.

## Verdict

**Not safe to execute as written.** The plan's *structure* is good — task ordering is
sensible, Task 5 is correctly independent of 2–4, dependency injection is used
consistently, and the storage/orchestration/view separation matches how V1–V3
actually work. The problem is concentrated in one place.

**The spec's "Client: `js/ics.js`" section needs rework, not patching.** Criticals 1,
2, 3, 5 and Major 9 are all the same root failure: the supported ICS subset was
specified from recollection of what ICS *is* rather than from what these four
providers *emit*, and the "skip unsupported" policy converts every gap in that
recollection into invisible data loss. Rewrite that section after Task 0 (Major 8)
puts real captured feeds in the repo — that ordering resolves five findings at once
and is the change I'd make first.

Three further design decisions must be made by a human before Task 7 can start,
because no implementer can resolve them correctly on their own:
- the `EventInstance` contract (Critical 4),
- List view's external horizon (Critical 6),
- view-cap policy when four feeds compete with own items (Major 14).

Critical 7 (`/feed` abuse) is independent of all of the above, is ~10 lines in Task
5, and should not ship without the `Origin` check.

With those addressed, the remaining Majors are ordinary plan-hardening — add the
tests, name the algorithms, split `worker/src/feed.js` — and the plan is executable.
